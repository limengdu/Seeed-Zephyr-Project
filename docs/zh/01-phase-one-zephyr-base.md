# 阶段 1: Zephyr Base

## 1. 目标

阶段 1 为 XIAO、Grove、扩展板和 Zephyr 构建可靠的技术基础。

目标不是创建一个精致的用户界面。目标是创建一个未来工具可以使用的可信事实来源。

在这一阶段结束时，Seeed 应该知道:

- 哪些 XIAO 开发板可以很好地配合 Zephyr 工作
- 哪些功能已支持、实验性支持、被阻塞或状态未知
- 哪些 Grove 模块可以用可复用方式表示
- 哪些示例可以编译
- 哪些示例可以在真实硬件上运行
- 应推荐哪个 Zephyr 版本

一句话总结: 阶段 1 把分散的 Zephyr 支持变成结构化、可测试、可复用的基础。

## 2. 核心原则

这个基础应对上游友好，并以产品为中心。

它不应变成 Zephyr 的私有 fork。长期维护一个 Seeed 专用 Zephyr fork 会制造升级阻力，割裂用户体验，并让安全维护变得更困难。

相反:

- board 和 driver 修复应尽可能贡献到上游
- 临时补丁应被清晰跟踪
- Seeed 专属产品元数据应保存在本仓库
- 示例应使用正常的 Zephyr 项目结构
- Grove 集成应在可行时使用 Zephyr 原生概念

一句话总结: 使用上游 Zephyr 作为基础，并在其周围添加 Seeed 的产品层。

### 元数据在哪里停止，Devicetree 从哪里开始

这是阶段 1 中最重要的边界。Zephyr 已经拥有一个硬件事实系统: Devicetree(设备树)、drivers 和 shields。这个仓库中的元数据不得用第二套并行格式重新描述这些事实，因为两个事实来源会逐渐偏离，元数据会悄悄开始说谎。

边界规则:

- Devicetree、drivers 和 Zephyr shields 拥有硬件事实: 哪个引脚是什么信号、模块位于哪条总线上、哪个 driver 绑定哪个传感器。
- 元数据只拥有产品层: 显示名称、分类、照片、文档链接、默认设置、推荐模板和验证状态。

Zephyr shield(扩展板描述) 是对附加板的可复用描述。它是 `boards/shields/<name>/` 下的真实文件夹，包含一个 `.overlay` 文件以及可选的 `Kconfig.shield` 默认值，Zephyr 在构建时通过标准 `--shield` 机制应用它。

实际影响:

- Seeed 扩展板应建模为真实的 Zephyr shield。它的元数据通过名称引用该 shield；它不重新列出引脚到信号的映射。
- Grove 模块的电气连接通过 Devicetree 表达，即 shield 总线上的一个节点或一个小 overlay，而不是通过 YAML 中手写的接线表表达。
- 当接线图或生成器需要引脚事实时，它从 shield overlay 读取，而不是从元数据中的第二份拷贝读取。

一句话总结: Devicetree 和 shields 保存硬件事实，元数据保存产品叙述，两者绝不能描述同一个事实两次。

## 3. 仓库职责

本仓库应拥有以下数据和资产。

### XIAO 开发板元数据

每块开发板都应有一个机器可读的元数据文件。该文件分为两个清晰分离的部分: 由人工或 AI 编写的 authored fields，以及只由工具根据 CI 和硬件测试结果写入的 derived fields。Derived fields 绝不能手动编辑；本节后面的“保持元数据真实”规则会解释原因。

Authored fields(身份和意图):

```yaml
id: xiao_esp32c6
display_name: Seeed Studio XIAO ESP32C6
zephyr_target: seeed_xiao_esp32c6
vendor: espressif
# Version policy is latest-stable. See section 6. The exact validated version
# is a derived field, established by CI evidence, not asserted here.
version_policy: latest_stable
```

Derived fields(观察到的现实，机器写入，作者只读):

```yaml
# Generated by tools/sync_status from CI and hardware-test artifacts.
# Each value carries provenance and falls back to unknown when evidence is stale.
status: experimental
validated_zephyr_version: v4.4.0
interfaces:
  gpio: tested
  i2c: tested
  spi: build-only
  uart: tested
  adc: unknown
  pwm: unknown
  wifi: experimental
  ble: experimental
  usb: tested
power:
  deep_sleep: unknown
validation:
  build: passed
  hardware: partial
known_issues:
  - id: esp32c6_wifi_pm_unverified
    severity: medium
    summary: Wi-Fi power management is not yet validated against ESP-IDF behavior.
evidence:
  last_ci_run: ci-2026-06-09-0042
  last_updated: 2026-06-09T00:00:00Z
```

一句话总结: authored half 说明这块板是什么，derived half 报告实际已经证明了什么。

### Grove 模块元数据

每个 Grove 模块也应有一个元数据文件。和开发板一样，authored fields 描述产品，derived fields 报告验证结果。模块的电气接线不列在这里；它通过所选 shield 上的 Devicetree 表达，后者保持为唯一的引脚事实来源。

Authored fields(身份和意图):

```yaml
id: grove_sht40
display_name: Grove Temperature and Humidity Sensor SHT40
category: sensor
interface: i2c
default_address: "0x44"
# Pointer into Zephyr's truth source, not a re-description of it.
zephyr_compatible: sensirion,sht4x
zephyr_driver: sht4x
required_configs:
  - CONFIG_SENSOR=y
  - CONFIG_SHT4X=y
power_rail: 3v3
supported_templates:
  - sensor_to_serial
  - sensor_to_mqtt
```

Derived fields(由 CI 和硬件测试机器写入):

```yaml
validation:
  build: passed
  hardware: tested
evidence:
  last_ci_run: ci-2026-06-09-0042
  last_updated: 2026-06-09T00:00:00Z
```

准确的总线引脚(SDA、SCL)有意缺席。它们存在于 shield overlay 中，该 overlay 将 Grove I2C 端口映射到开发板的 I2C 控制器，因此对 shield 的一次修改会同时更新所有地方的接线信息。

一句话总结: Grove 元数据命名模块并指向它的 Zephyr driver，而 Devicetree 保留接线事实。

### 扩展板元数据

扩展板应作为一等对象处理，因为 Grove 用户经常通过 shield 或扩展板连接模块。每块 Seeed 扩展板都应实现为真实的 Zephyr shield，它的元数据应引用该 shield，而不是重新列出引脚映射。

Authored fields:

```yaml
id: xiao_grove_shield
display_name: XIAO Grove Shield
compatible_form_factor: xiao
# The hardware truth lives in this shield's overlay, not below.
zephyr_shield: seeed_xiao_grove_shield
# Product-facing labels only: which ports a user can physically see.
# These are labels for the UI, not the pin-routing source of truth.
ports:
  - id: i2c_0
    type: i2c
    label: Grove I2C
  - id: d0
    type: gpio
    label: Grove D0
```

对应的 shield 携带实际路由:

```text
boards/shields/seeed_xiao_grove_shield/
  seeed_xiao_grove_shield.overlay   # maps Grove I2C port to the XIAO I2C controller
  Kconfig.shield
```

因为 overlay 是唯一写明“Grove I2C SDA 是这个控制器的 SDA”的地方，所以接线修复只需在 Zephyr 自己的格式中修改一次，所有读取该 shield 的工具都能看到它。

一句话总结: 扩展板元数据命名 shield 及其可见端口，而 shield overlay 拥有实际引脚路由。

### 示例和样例

初始样例应小而便于诊断。

推荐的基线样例:

- blinky
- button
- serial_log
- i2c_scan
- adc_read
- pwm_fade
- sensor_basic
- ble_beacon
- wifi_mqtt

第一批应聚焦最短的有用路径:

```text
build -> flash -> boot -> log -> peripheral -> Grove module
```

一句话总结: 基线样例是开发板和模块的健康检查。

### 兼容性矩阵

兼容性矩阵应从元数据和 CI 结果生成或验证。

状态术语应明确:

- `tested`: 已在真实硬件上验证
- `build-only`: 编译验证通过，但未测试硬件
- `experimental`: 预期可工作，但还不够稳定，不适合推荐
- `blocked`: 已知问题阻止正常使用
- `unsupported`: 因设计或硬件限制而不支持
- `unknown`: 尚未评估

一句话总结: 矩阵应说真话，而不只是宣传支持。

### 保持元数据真实: 状态是派生的，不是声明的

像 `tested` 这样的状态词，只有在不能被手动设置后任其腐烂时才可信。因此，整个系统的核心规则是:

```text
Status fields are outputs of testing, never inputs typed by a person.
```

这区分了两类字段，也就是开发板和 Grove 示例中已经展示的两类:

- Authored fields 描述身份和意图。由人工或 AI 编写: ids、names、drivers、required configs、templates。
- Derived fields 描述观察到的现实。只由工具写入: build status、hardware status、validated Zephyr version、per-interface status、known issues、evidence。

同步工作方式:

1. CI 运行构建矩阵和硬件在环矩阵。每个开发板、样例和模块组合都会产生一个机器可读结果(pass、fail 或 skipped)，以及使用的 Zephyr 版本和 commit。
2. `tools/sync_status` 读取这些结果产物，并把 derived fields 写入 `metadata/status/`，该目录与 authored files 物理分离，因此没人会手动编辑它们。
3. `tools/render_docs` 根据 derived files 构建兼容性矩阵。矩阵展示证据，而不是主张。

三条规则让状态难以伪造:

- 来源记录。每个派生值都记录它来自哪次 CI 运行、哪个 Zephyr 版本、哪个 commit，以及何时产生。没有证据记录的 `tested` 是无效的。
- 过期降级。绿色状态只有在拥有新鲜的通过证据时才有效。如果最新运行失败、被跳过，或者早于定义的时间窗口，状态会自动回退到 `unknown` 或 `blocked`。绿色不能靠旧数据一路滑行。
- 漂移检查。一个 CI 步骤会比较 authored intent 和 derived evidence。如果 authored file 暗示了证据不支持的能力，或者某个 `id` 或 driver 在固定的 Zephyr tree 中不再能解析，检查就会让构建失败。这能阻止元数据悄悄说谎。

一句话总结: 测试写入状态，新鲜度保持状态真实，漂移检查会在叙述和证据不一致时让构建失败。

## 4. 建议目录结构

```text
metadata/
  boards/                 # authored board fields
  grove_modules/          # authored Grove fields
  expansion_boards/       # authored expansion-board fields
  templates/
  status/                 # derived fields, machine-written, read-only to authors
  compatibility/          # generated matrix output

boards/
  shields/                # Seeed expansion boards as real Zephyr shields (overlay + Kconfig)

samples/
  blinky/
  serial_log/
  i2c_scan/
  sensor_basic/

templates/
  west-basic/
  west-sensor/
  platformio-basic/
  platformio-sensor/

tools/
  validate_metadata/      # schema + authored/derived separation checks
  build_matrix/           # runs the CI build sweep
  sync_status/            # writes derived status from CI/HIL artifacts
  render_docs/

tests/
  compile_matrix/
  hardware_matrix/

docs/
  board-matrix.md
  grove-matrix.md
  getting-started.md
```

注意: 独立的 `overlays/` 抽屉被有意移除。每块开发板和每个端口的接线现在都位于 `boards/shields/` 下各自的 Zephyr shield 中，因此引脚事实只有一个归属地，而不是两个。

一句话总结: 把 authored facts、derived status、shields、samples、templates、tools、tests 和 documentation 放在分开的抽屉里。

## 5. 验证策略

### 构建验证

在可行的情况下，每个受支持的开发板和样例组合都应由 CI 编译。

构建验证回答:

```text
Does this project compile with the recommended Zephyr version?
Did a metadata or template change break any generated project?
Which board, module, or template caused the failure?
```

一句话总结: 构建验证会在用户遇到之前捕获损坏的示例。

### 硬件在环验证

Hardware-in-loop(硬件在环) 意味着系统测试真实开发板和真实 Grove 模块，而不是只编译代码。

第一批硬件测试应保持简单:

- flash 成功
- boot 成功
- serial output 包含预期文本
- I2C scan 找到预期地址
- sensor value 存在且处于合理范围内

硬件在环应从少量高价值组合开始。

一句话总结: 真实硬件测试证明示例不只是在编译器层面可用。

### 功耗和性能验证

不应假设 Zephyr 会自动匹配供应商 SDK 的性能。

对选定开发板，比较:

- 启动时间
- 固件大小
- RAM 使用量
- 工作电流
- 睡眠电流
- 唤醒时间
- Wi-Fi 或 BLE 稳定性

目标不总是击败供应商 SDK。目标是知道 Zephyr 在哪里足够好，以及供应商 SDK 在哪里仍然是更好的推荐。

一句话总结: 性能数据能防止 Zephyr 变成盲目的战略押注。

## 6. 版本策略

Zephyr 变化频繁。用户需要可复现的构建。本项目的基线是最新的 Zephyr 稳定版本。稳定版本经过充分测试，并携带最新的开发板和 driver 支持，这一点很重要，因为 XIAO 产品线包含较新的芯片。

Zephyr 大约每六个月发布一个稳定版本，每个稳定版本都会在有限窗口内维护，直到下一个版本发布。因此，基线预期会按这个节奏向前移动，而不是固定多年不变。

策略:

- 基线是当前最新稳定版本(本文写作时为 Zephyr 4.4)。
- 将样例和模板验证锁定到该版本。
- 当新的稳定版本发布时，按计划测试升级并向前移动基线。
- 如果某块开发板的上游支持尚未进入当前稳定版本，则将其标记为 pending，并在它进入稳定版本后进行验证。对这类开发板使用开发分支只是临时例外，不是基线。
- 版本按开发板记录。`version_policy` authored field 声明意图(`latest_stable`)；`validated_zephyr_version` derived field 记录 CI 已证明的准确版本。

一句话总结: 跟踪最新稳定 Zephyr 版本，按大约六个月的节奏向前移动，并让 CI 证据记录每块开发板验证过的准确版本。

## 7. 阶段 1 成功标准

当满足以下条件时，阶段 1 应视为成功:

- 至少五块有代表性的 XIAO 开发板拥有元数据
- 至少十个高频 Grove 模块拥有元数据
- 至少一块扩展板被表示
- 基线样例在 CI 中可编译
- 选定组合通过硬件验证
- 兼容性状态可见且可复现
- Zephyr 限制被诚实记录

一句话总结: 当 Seeed 能证明什么可用、什么不可用、什么仍未知时，阶段 1 就成功了。

## 8. 阶段 1 非目标

阶段 1 不应包括:

- 完整在线 IDE
- 完整 VS Code 插件
- 完整 Wokwi 风格模拟器
- 庞大的 Seeed 专用 SDK 抽象层
- 所有 XIAO 开发板
- 所有 Grove 模块
- 复杂的 Matter、AI 或摄像头项目

一句话总结: 阶段 1 应专注于证据和基础。
