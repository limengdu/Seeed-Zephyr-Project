# 路线图与风险

## 1. 路线图概览

推荐路线图包含三个主要阶段:

```text
Phase 1: Zephyr Base
Phase 2: CLI Generator
Phase 3: VS Code Plugin
```

每个阶段都应为下一阶段创建可复用资产。

一句话总结: 先构建基础，再构建生成器，最后构建产品界面。

## 2. 阶段 1 路线图

### 持续时间

推荐持续时间:

```text
8 to 12 weeks
```

### 主要工作

- 定义元数据 schema
- 添加有代表性的 XIAO 开发板元数据
- 添加有代表性的 Grove 元数据
- 添加扩展板元数据
- 添加基线样例
- 配置 CI 构建验证
- 运行选定的硬件在环测试
- 将选定 Zephyr 行为与供应商 SDK 对比

### 交付物

- 开发板元数据
- Grove 元数据
- 扩展板元数据
- 基线样例
- 兼容性矩阵
- CI 构建工作流
- 硬件验证报告
- Zephyr 版本推荐

### 进入阶段 2 的门槛

只有在满足以下条件时才进入阶段 2:

- 有代表性的 XIAO 开发板可以构建基线样例
- 高频 Grove 模块可以被一致地描述
- 生成或手动整理的矩阵数据可信
- 硬件验证显示足够的真实世界价值

一句话总结: 阶段 1 通过证明基础真实存在，赢得构建工具的资格。

## 3. 阶段 2 路线图

### 持续时间

推荐持续时间:

```text
8 to 10 weeks
```

### 主要工作

- 实现 CLI 骨架
- 实现 list、check、generate、verify、build 命令
- 支持 west 项目输出
- 支持初始模板
- 生成 README 和接线资产
- 包含项目元数据快照
- 添加生成项目的 CI 测试
- 在 west 稳定后添加 PlatformIO 输出

### 交付物

- CLI 包
- 项目生成器
- west 模板
- 初始 PlatformIO 模板
- 生成项目示例
- CLI 测试套件
- 生成项目的构建验证

### 进入阶段 3 的门槛

只有在满足以下条件时才进入阶段 3:

- 生成的项目是确定性的
- 生成的项目可可靠构建
- CLI 错误清晰
- 元数据和模板可以支持图形界面

一句话总结: 阶段 2 通过证明项目生成可靠，赢得构建插件的资格。

## 4. 阶段 3 路线图

### 持续时间

推荐 MVP 持续时间:

```text
10 to 16 weeks
```

### 主要工作

- 创建 VS Code extension 骨架
- 构建 Webview 配置器
- 加载硬件 catalog
- 显示兼容性结果
- 渲染接线图
- 实现设置面板
- 调用 CLI 生成项目
- 集成一键交接到官方 Zephyr 扩展，用于构建和烧录
- 添加 XIAO 和 Grove 特定错误提示

### 交付物

- VS Code plugin MVP
- 硬件选择 UI
- Grove 选择 UI
- 扩展板选择 UI
- 接线图视图
- 项目生成流程
- 一键交接到官方 Zephyr 扩展的构建和烧录
- XIAO 和 Grove 错误提示
- 早期用户测试报告

### 进入公开 Beta 的门槛

只有在满足以下条件时才进入公开 beta:

- 插件至少可在 macOS 和 Windows 上工作，或有一个清晰定义的首个操作系统
- 生成的项目可以通过官方 Zephyr 扩展在本地构建
- 接线图已验证
- 与官方扩展的交接可在干净环境中工作
- XIAO 和 Grove 特定错误能产生清晰提示
- 早期测试者可以在没有工程师手把手帮助的情况下完成项目

一句话总结: 阶段 3 在产品流程真正服务真实用户，而不只是服务内部工程师时才算成功。

## 5. 技术风险

### 风险: Zephyr 对不同芯片的支持不均衡

有些芯片可能拥有强大的 Zephyr 支持。其他芯片在高级无线、低功耗或外设功能上可能严重依赖供应商 SDK。

缓解措施:

- 保持状态真实
- 将选定功能与供应商 SDK 对比
- 采用 Zephyr-first，而不是 Zephyr-only
- 保留供应商 SDK 路径文档

一句话总结: 不要假设 Zephyr 在每颗芯片上都同样强。

### 风险: 低功耗性能不够好

低功耗行为通常依赖芯片特定 SDK 细节。

缓解措施:

- 在有代表性的开发板上测量电流、睡眠和唤醒行为
- 清楚标记低功耗模板为 tested 或 experimental
- 在 Zephyr 没有竞争力的地方推荐供应商 SDK

一句话总结: 功耗主张必须测量，而不能假设。

### 风险: 元数据变得不正确

不正确的元数据可能生成错误接线、错误 overlays 或错误配置。

缓解措施:

- 验证元数据 schema
- 要求审查元数据变更
- 将元数据连接到 CI 构建
- 将选定元数据连接到硬件测试
- 包含生成项目快照

一句话总结: 元数据是产品的事实来源，因此必须像代码一样测试。

### 风险: CLI 和插件逻辑分叉

如果插件重新实现生成逻辑，bug 会成倍增加。

缓解措施:

- 将生成保留在 CLI 中
- 让插件调用 CLI
- 共享元数据和验证规则

一句话总结: 一个生成器应服务每一种界面。

### 风险: 插件范围扩展太快

试图同时构建 CubeMX、Wokwi、PlatformIO 和 AI 助手，会延迟真实验证。

缓解措施:

- 定义一个小型 MVP
- 第一版避免完整仿真
- 先支持 west，再支持 PlatformIO
- 限制初始开发板和模块数量

一句话总结: 一个较小但完整的流程，胜过一个庞大但未完成的平台。

## 6. 商业风险

### 风险: 用户不想使用 Zephyr

许多入门用户可能更喜欢 Arduino、MicroPython 或 CircuitPython。

缓解措施:

- 将 Zephyr 复杂性隐藏在生成项目背后
- 在有价值的地方保留 Arduino 支持
- 先面向专业和半专业用户
- 衡量实际采用情况

一句话总结: 用户不应在获得价值前被迫学习 Zephyr。

### 风险: 项目没有降低内部成本

如果系统增加的维护工作超过它减少的维护工作，就会失去商业价值。

缓解措施:

- 跟踪通过元数据减少的重复文档工作
- 跟踪插件发布前后的 issue 类别
- 使用 CI 和生成文档减少手工工作

一句话总结: 项目必须减少重复工作，而不是制造新的维护负担。

### 风险: 糟糕地重复已有工具

用户已经拥有 Zephyr、官方 Zephyr VS Code 扩展、nRF Connect 等供应商扩展、PlatformIO 和其他供应商工具。这些工具已经提供构建、烧录、监视、调试和环境设置，并且已经成熟。

因此，本项目的决定很明确: 不重新实现工具链。阶段 3 只负责独特的构建前价值，即硬件选择、兼容性、接线、配置和生成，并交接给官方扩展进行构建和烧录。

缓解措施:

- 聚焦 XIAO + Grove 产品体验
- 不尝试替代通用嵌入式工具或官方 Zephyr 工具链扩展
- 与现有工具集成，而不是对抗它们，并依赖官方 Zephyr 扩展进行构建和烧录

一句话总结: 项目的独特价值是 Seeed 硬件组合，因此它构建在官方工具链之上，而不是重建它。

## 7. 建议指标

### 基础指标

- 拥有元数据的 XIAO 开发板数量
- 拥有元数据的 Grove 模块数量
- 拥有元数据的扩展板数量
- CI 测试过的示例数量
- 硬件测试过的组合数量
- 已记录的已知问题数量

### 生成器指标

- 模板数量
- 生成项目构建成功率
- 平均生成时间
- 带有 README 和接线输出的生成项目百分比
- 使用元数据快照复现的 bug 报告数量

### 插件指标

- 完成第一个项目的时间
- 生成后的构建成功率，在官方 Zephyr 扩展中衡量
- 从生成到启动构建的交接成功率
- 通过官方扩展完成 build、flash 和 monitor 的用户数量
- 减少的支持问题数量

一句话总结: 衡量系统是否改善真实流程，而不只是文件是否更多。

## 8. 推荐初始范围

初始开发板:

- XIAO ESP32C6
- XIAO ESP32S3
- XIAO nRF54L15
- XIAO MG24
- XIAO RP2350 or XIAO RA4M1

初始 Grove 模块:

- Grove SHT40
- Grove Button
- Grove Relay
- Grove Light Sensor
- Grove OLED
- Grove IMU

初始模板:

- blinky
- i2c_scan
- sensor_to_serial
- button_to_serial
- relay_control

一句话总结: 在扩展到高级项目之前，先从有代表性的硬件和简单场景开始。

## 9. 最终建议

只有在保持聚焦的情况下，这一策略才值得推进:

```text
Upstream Zephyr for core OS and board support.
Seeed Zephyr Base for XIAO and Grove product metadata.
CLI for deterministic project generation.
VS Code plugin for developer experience.
Vendor SDKs for advanced chip-specific scenarios.
```

一句话总结: 胜出的架构不是一个巨型平台，而是一个职责清晰的分层系统。
