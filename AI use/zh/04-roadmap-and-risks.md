# 路线图与质量控制

## 1. 路线图概览

路线图分为三个阶段:

```text
阶段 1: 示例、项目、元数据与验证基础
阶段 2: 用于发现、构建、验证和生成的 CLI
阶段 3: VS Code 产品体验
```

每个阶段都必须保持同一个产品中心: 经过验证的 XIAO + Grove Zephyr 示例和项目。

一句话总结: 路线图先建设用户能运行的内容，再围绕内容增加工具。

## 2. 阶段 1 路线图

主要工作:

- 创建首批 `examples/boards/` 资产
- 创建首批 `examples/grove/` 资产
- 创建首批 `examples/expansion_boards/` 资产
- 创建首批完整 `projects/`
- 定义 examples 和 projects metadata
- 验证开发板/模块 metadata
- 从仓库根目录构建示例
- 记录 build-only 和 hardware-tested 证据
- 定义贡献要求

进入阶段 2 的门槛:

- 本仓库自己的示例已经存在
- 至少一个示例能通过项目工具构建
- metadata 验证通过
- 构建矩阵覆盖首批示例
- 贡献结构已经文档化

一句话总结: 阶段 1 通过证明没有生成器时仓库也已经有用，才进入阶段 2。

## 3. 阶段 2 路线图

主要工作:

- 实现 CLI 骨架
- 列出开发板、模块、能力、示例和项目
- 构建仓库示例和项目
- 验证贡献结构
- 从已知示例复制/创建项目
- 支持生成项目快照
- 让 CI 调用同一套命令

进入阶段 3 的门槛:

- CLI 可以操作真实示例/项目
- 生成项目来自已知资产
- 错误具体且可操作
- CI 可以验证示例和项目

一句话总结: 阶段 2 通过让目录可操作，才进入阶段 3。

## 4. 阶段 3 路线图

主要工作:

- 构建 VS Code extension 骨架
- 浏览示例和项目
- 按开发板、Grove 模块、能力和状态筛选
- 预览接线和验证证据
- 通过 CLI 创建项目
- 把 build/flash/monitor/debug 交给官方 Zephyr 工具
- 暴露贡献检查

进入公开 beta 的门槛:

- 早期用户可以找到示例并运行
- 生成/复制出的项目能通过官方工具构建
- 接线图已验证
- 贡献检查可用
- 用户可以在没有工程师手把手帮助的情况下完成第一个 XIAO + Grove Zephyr 项目

一句话总结: 阶段 3 成功时，UI 让验证过的目录更容易使用。

## 5. 质量控制

### 控制点: 当前项目上下文

由于大量工作可能由 AI 完成，未来工作在实现前需要一份简洁、最新、项目级的说明。

必需做法:

- 所有 AI-facing strategy 放在 `AI use/`
- 要求维护 `AI use/README.md` 和 `AI use/WORKLOG.md`
- 每个阶段都围绕示例、项目、验证和贡献来写
- 用事实性 work log 记录重要工作

一句话总结: AI 工作应从项目说明开始，并留下清晰交接轨迹。

### 控制点: Setup 指向内容

Setup 脚本负责把用户带到仓库内容。

必需做法:

- setup 脚本最后必须指向仓库示例/项目
- getting-started 文档必须解释从本仓库构建什么
- 成功指标必须计算示例和项目

一句话总结: setup 是进入仓库示例和项目的入口。

### 控制点: Metadata 由内容支撑

metadata 能导向真实示例或项目时价值最高。

必需做法:

- 每次扩展 metadata 都应配套示例计划
- 阶段 1 成功要求本仓库自己的示例
- build matrix 应从通用上游 sample 转向仓库示例

一句话总结: metadata 通过帮助用户到达可用内容来产生价值。

### 控制点: 社区示例有验证证据

社区示例在结构清晰且有证据时增加价值。

必需做法:

- 定义贡献要求
- 诚实接受 build-only 状态
- 只有证据充分时才提升为 hardware-tested
- 要求预期输出和硬件说明

一句话总结: 社区内容既要欢迎，也要验证。

### 控制点: Zephyr 支持由证据驱动

不同 XIAO 芯片在无线、低功耗和高级外设上的 Zephyr 支持程度不同。

必需做法:

- 保持状态真实
- 选择性对比供应商 SDK
- 在更好时记录供应商 SDK 路径
- 明确标注限制

一句话总结: Zephyr-first 始终由证据驱动。

## 6. 指标

内容指标:

- 开发板示例数量
- Grove 示例数量
- 扩展板示例数量
- 完整项目数量
- 接受的社区贡献数量

证据指标:

- build-only 示例数量
- hardware-tested 示例数量
- hardware-tested 项目数量
- 已记录已知问题数量

工具指标:

- 示例可从仓库根目录构建
- 生成项目可成功构建
- 贡献验证能发现结构错误
- 用户比手动搜索 Zephyr 更快找到并运行第一个示例

一句话总结: 先衡量内容有用性，再衡量工具。

## 7. 推荐初始范围

初始示例:

- `xiao_esp32c3/hello_world`
- `xiao_esp32c6/blinky`
- `xiao_esp32c6/i2c_scan`
- 一个 Grove sensor `basic_read`
- 一个扩展板 display 或 button 示例

初始项目:

- 一个 XIAO + Grove sensor-to-serial 项目
- 一个 XIAO + display 项目
- 一个无线或 BLE 项目，在板级支持被证明后再做

一句话总结: 从一个用户真的能运行的小目录开始。
