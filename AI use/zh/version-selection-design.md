# 版本选择设计

状态: 设计草案，待审阅。本文件只描述方案，不代表已实现的行为。

## 1. 要解决的问题

用户希望 CLI 像 ESP-IDF 那样: 自由选择一个版本，并使用与该版本匹配的示例，而不是每次都跟着仓库最新版本走。

本仓库的版本不是一个数字，而是一对:

```text
仓库版本（示例、metadata、CLI 代码） + 它锁定的 Zephyr 版本
```

两边必须一起切换。只切一边会出现“构建通过、真机失效”的结果。

## 2. 为什么必须成对切换

Zephyr v4.5.0 的板级文件查找会先把 `xiao_rp2350/rp2350a/m33` 改写成
`xiao_rp2350/rp2350a/m33_0`，再去找板级文件。旧版本仓库的文件名是
`xiao_rp2350_rp2350a_m33.*`，在新版本下不会被应用，串口静默回退到 `&uart0`，USB 串口和
UF2 自动进入都失效，而构建本身显示成功。

这个事实决定了设计的底线: 版本不匹配时构建成功不能当作正确。CLI 要在构建前告知用户当前组合是否配对。

## 3. 现状

已有的基础:

- `seeed-zephyr update --version <版本>` 在仓库模式下会切换仓库签出。候选名依次为
  原样输入、`v<版本>`、`seeed-zephyr-<版本>`，切换前要求工作区干净。
- `create` 写入的 `snapshot.json` 带有 `zephyr_version` 字段，值来自常量 `ZEPHYR_BASELINE`。
- `seeed-zephyr info` 能打印当前 CLI 所认为的基线版本。

缺口:

| 点 | 现状 |
| --- | --- |
| Zephyr 工作区 | 全机只有一份 `~/zephyrproject`，setup 脚本会就地把它移到脚本锁定的版本 |
| 版本校验 | `build --app` 不读 `snapshot.json`，不比对实际安装的 Zephyr 版本 |
| 基线报告 | `info` 打印的是代码里的常量，不是磁盘上的 Zephyr 版本 |
| 发布标记 | 仓库目前没有 git tag，`--version` 没有可选的发布版本 |
| 映射表 | 没有“仓库版本 ↔ Zephyr 版本”的数据文件 |
| 编辑器插件 | 只管理 CLI 自身的版本，不感知 Zephyr 工作区版本 |

## 4. 目标体验

```text
seeed-zephyr versions                 列出可用版本对和已安装状态
seeed-zephyr install v1.1.0           安装该版本对（仓库签出 + 匹配的 Zephyr）
seeed-zephyr use v1.1.0               把该版本对设为当前使用的版本
seeed-zephyr build <board> --app .    按项目 snapshot 选择工作区，不匹配时提示
```

`versions` 的输出应该让用户一眼看出三件事: 有哪些版本对、每个对应哪个 Zephyr、本机安装了哪些。

## 5. 版本映射表

新增一份数据文件，例如 `metadata/versions.yaml`，每行一个版本对:

```yaml
versions:
  - id: v1.1.0
    zephyr: v4.5.0
    sdk: "1.0.1"
  - id: v1.0.0
    zephyr: v4.4.0
    sdk: "1.0.1"
```

约定:

- `id` 是仓库的 git tag，也是用户在命令里输入的名字。
- 一个仓库 tag 只对应一个 Zephyr 版本。换 Zephyr 版本就发一个新 tag。
- 这份文件随仓库一起版本化。旧 tag 里的映射表不知道更新的版本，所以“有哪些版本可选”以远程 tag 列表为准，映射内容以该 tag 自己的文件为准。
- 校验器要求: 当前仓库的 `ZEPHYR_BASELINE` 常量与映射表里最新一行的 `zephyr` 一致。

## 6. 目录布局

Zephyr 工作区按版本并排，共享一份 SDK:

```text
~/zephyrproject/v4.4.0/      一个完整的 west 工作区
~/zephyrproject/v4.5.0/      另一个完整的 west 工作区
~/zephyr-sdk-1.0.1/          多个工作区共享，SDK 主版本一致时不重装
```

仓库签出按版本并排:

```text
~/.seeed-zephyr/versions/v1.0.0/    该 tag 的完整签出
~/.seeed-zephyr/versions/v1.1.0/
~/.seeed-zephyr/current              指向当前使用的签出
```

选择并排而不是就地切换，是因为就地切换会让旧项目失去对应的工作区。并排后，每个已生成的项目都能找回它创建时的那一对。

每个 Zephyr 工作区占用数 GB 磁盘，west 的 blobs 也随工作区复制一份。默认只维护最新版本和上一个版本，更早的版本由用户按需安装。

## 7. 构建时怎么选工作区

`seeed-zephyr build <board> --app <目录>` 的选择顺序:

1. 读目录里的 `snapshot.json`，取出 `zephyr_version`。
2. 对应版本的工作区已安装时，用它来构建。
3. 没有 `snapshot.json` 的目录（仓库里的示例本身、手写项目）用当前选中的版本对。
4. 工作区未安装时，打印一行安装命令并停下，不自动下载数 GB 的内容。
5. 环境变量 `ZEPHYR_WORKSPACE` 仍然优先，保留给构建矩阵和排查使用。

不匹配提示的判定: 当目录的 `zephyr_version` 与实际用于构建的工作区版本不同时，构建前打印一行说明两边的版本。提示之后继续构建，因为排查时需要故意用错配的组合。

`info` 增加两行: 实际使用的 Zephyr 工作区路径，以及该工作区当前的版本。这两行来自磁盘，不来自代码常量。

## 8. 与现有机制的关系

- `update --version` 保留，语义改为“切换当前使用的版本对”，内部走和 `use` 相同的路径，避免两套逻辑。
- setup 脚本里的就地迁移（`sync_manifest_revision`）只对“还没有版本子目录”的旧工作区生效一次: 把现有的 `~/zephyrproject` 整体移入 `~/zephyrproject/v4.4.0/`，之后各版本目录互不干扰。判断依据是目录里是否已经有 `.west`。
- 包模式（pip、pipx、Homebrew）下，示例和 metadata 随包版本走。`versions` 和 `use` 在包模式下操作的是并排的仓库签出，不改动已经安装的那份包。Homebrew 安装仍然不支持在包管理器里回退版本。
- VS Code 插件目前直接读 metadata 并过滤掉 `unsupported`。插件侧的改动是让版本选择界面调用同一组 CLI 命令，并在环境信息里显示当前版本对。这一步放在 CLI 命令稳定之后。

## 9. 分期

第 1 期，让旧项目能找回自己的工作区:

1. 工作区改成按版本子目录并排，setup 脚本完成一次性迁移。
2. `build --app` 按 `snapshot.json` 选择工作区，不匹配时打印提示。
3. `info` 打印实际工作区路径和版本。

第 1 期不新增命令，不依赖 git tag，可以单独验证: 用 v4.4.0 时代生成的项目，在机器上同时存在两个工作区时，构建仍然走 v4.4.0。

第 2 期，让用户能选版本:

1. 给当前基线打第一个仓库 tag，建立映射表。
2. 实现 `versions`、`install`、`use`，以及按版本并排的仓库签出。
3. 更新入门文档，说明版本对和磁盘占用。
4. 插件接入同一组命令。

## 10. 验证方式

- 单元测试覆盖: 有 snapshot 时选对工作区、没有 snapshot 时用当前版本、工作区缺失时给出安装命令、环境变量优先、旧工作区迁移一次后不再移动。
- 一次真实构建: 同一台机器上并存 v4.4.0 与 v4.5.0 工作区，用两个版本分别构建 RP2350 示例，确认串口节点来自对应版本的板级文件。
- 文档与命令帮助保持一致: 新命令出现在 `seeed-zephyr --help` 和入门文档里。

## 11. 不在本次范围内

- 不改变示例内容和板级支持范围。nRF54LM20A、nRF54LM20B、STM32C5 仍按原计划单独推进。
- 不引入新的第三方依赖。版本切换用 git 与 west 完成。
- 不做自动清理旧工作区。删除数 GB 的目录由用户显式执行。
