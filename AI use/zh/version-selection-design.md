# 版本选择设计

状态: 设计草案，待审阅。本文件只描述方案，不代表已实现的行为。

## 1. 要解决的问题

用户希望 CLI 像 ESP-IDF 那样: 自由选择一个版本，并使用与该版本匹配的示例，而不是每次都跟着仓库最新版本走。

本仓库的版本不是一个数字，而是一对:

```text
仓库版本（示例、metadata、CLI 代码） + 它锁定的 Zephyr 版本
```

两边必须一起切换。只切一边会出现“构建通过、真机失效”的结果。

## 2. 为什么必须成对切换

Zephyr v4.5.0 的板级文件查找会先把 `xiao_rp2350/rp2350a/m33` 改写成
`xiao_rp2350/rp2350a/m33_0`，再去找板级文件。旧版本仓库的文件名是
`xiao_rp2350_rp2350a_m33.*`，在新版本下不会被应用，串口静默回退到 `&uart0`，USB 串口和
UF2 自动进入都失效，而构建本身显示成功。

这个事实决定了设计的底线: 版本不匹配时构建成功不能当作正确。CLI 要在构建前告知用户当前组合是否配对。

## 3. 现状

已有的基础:

- `seeed-zephyr update --version <版本>` 在仓库模式下会切换仓库签出。候选名依次为
  原样输入、`v<版本>`、`seeed-zephyr-<版本>`，切换前要求工作区干净。
- `create` 写入的 `snapshot.json` 带有 `zephyr_version` 字段，值来自常量 `ZEPHYR_BASELINE`。
- `seeed-zephyr info` 能打印当前 CLI 所认为的基线版本。

缺口:

| 点 | 现状 |
| --- | --- |
| Zephyr 工作区 | 全机只有一份 `~/zephyrproject`，setup 脚本会就地把它移到脚本锁定的版本 |
| 版本校验 | `build --app` 不读 `snapshot.json`，不比对实际安装的 Zephyr 版本 |
| 基线报告 | `info` 打印的是代码里的常量，不是磁盘上的 Zephyr 版本 |
| 发布标记 | 仓库目前没有 git tag，`--version` 没有可选的发布版本 |
| 映射表 | 没有“仓库版本 ↔ Zephyr 版本”的数据文件 |
| 编辑器插件 | 只管理 CLI 自身的版本，不感知 Zephyr 工作区版本 |

## 4. 目标体验

```text
seeed-zephyr versions                 列出可用版本对和已安装状态
seeed-zephyr install v1.1.0           安装该版本对（仓库签出 + 匹配的 Zephyr）
seeed-zephyr use v1.1.0               切换到该版本对，装过的版本约 10 秒、不联网
seeed-zephyr build <board> --app .    按项目 snapshot 核对版本，不一致时停下并给出命令
```

`versions` 的输出应该让用户一眼看出三件事: 有哪些版本对、每个对应哪个 Zephyr、本机安装了哪些。

## 5. 版本映射表

新增一份数据文件，例如 `metadata/versions.yaml`，每行一个版本对:

```yaml
versions:
  - id: v1.1.0
    zephyr: v4.5.0
    sdk: "1.0.1"
  - id: v1.0.0
    zephyr: v4.4.0
    sdk: "1.0.1"
```

约定:

- `id` 是仓库的 git tag，也是用户在命令里输入的名字。
- 一个仓库 tag 只对应一个 Zephyr 版本。换 Zephyr 版本就发一个新 tag。
- 这份文件随仓库一起版本化。旧 tag 里的映射表不知道更新的版本，所以“有哪些版本可选”以远程 tag 列表为准，映射内容以该 tag 自己的文件为准。
- 校验器要求: 当前仓库的 `ZEPHYR_BASELINE` 常量与映射表里最新一行的 `zephyr` 一致。

## 6. 存储方式: 一份工作区，多版本存档

全机只保留一份 Zephyr 工作区 `~/zephyrproject`。多个版本共存的方式是: 每个版本的压缩存档（git 对象）都放在这一份工作区里，任意时刻只展开其中一个版本的源文件。切换版本就是在本地把另一个版本重新展开。

三项机制都是 west 自带的，不引入新依赖:

| 机制 | 作用 | 配置 |
| --- | --- | --- |
| 模块筛选 | 只拉取本仓库开发板用到的模块 | `manifest.project-filter` |
| 本地离线切换 | 用已有存档展开另一个版本 | `west update -n` |
| 二进制文件缓存 | 按 sha256 缓存 blobs，切换时本地拷贝 | `blobs.auto-cache` |

模块筛选的保留清单: Zephyr 本体，加上 cmsis、cmsis_6、hal_atmel、hal_espressif、hal_nordic、hal_renesas、hal_rpi_pico、hal_silabs、mbedtls、mcuboot、picolibc、segger、tf-psa-crypto、zcbor。这份清单由开发板 metadata 推导，新增开发板时同步更新（例如支持 STM32C5 时加入 hal_stm32）。

每个已安装版本在每个模块里留一个本地引用 `refs/seeed/<版本>`，用来防止 git 清理时删掉不在当前展开状态的存档。

SDK 继续共用 `~/zephyr-sdk-<版本>`，映射表里 `sdk` 字段相同的版本对不重复安装。Python 环境（`.venv`）也共用一份，setup 按映射表里所有已安装版本的依赖清单合并安装。

## 7. 实测数据

2026-11-09 在隔离工作区里实测 v4.4.0 与 v4.5.0 共存与切换，仓库内容分别取自基线升级前后的两个提交:

| 项目 | 结果 |
| --- | --- |
| 完整工作区（68 个模块，用户现有） | 6.3G |
| 筛选后，单个版本 | 2.2G |
| 存档: 单版本 / 两个版本 | 228M / 261M，清理后 244M |
| 二进制文件缓存: 两个版本 | 184M |
| 首次安装第二个版本 | 源码 8 秒 + 模块 36 秒 + 二进制文件 274 秒 |
| 已装版本之间切换（无缓存） | 源码约 10 秒 + 二进制文件约 280 秒 |
| 已装版本之间切换（有缓存） | 源码约 10 秒 + 二进制文件 0 到 1 秒，全程离线 |
| v4.4.0 构建矩阵 | 10 通过、1 不支持，与 v4.4.0 时代记录一致 |
| v4.5.0 构建矩阵（切换后） | 11 通过 |
| RP2350 串口，两个版本各配自己的仓库 | 都是 `&cdc_acm_uart0` |
| git 清理后两个版本的存档 | 全部保留 |

结论: 每多保留一个版本，磁盘约多 0.1 到 0.2G；装过的版本之间切换约 10 秒，不联网。

## 8. 构建时怎么对版本

`seeed-zephyr build <board> --app <目录>` 的判定:

1. 读目录里的 `snapshot.json`，取出 `zephyr_version`。
2. 与工作区当前展开的版本一致时，直接构建。
3. 不一致且该版本已安装时，打印一行说明两边的版本，并给出 `seeed-zephyr use <版本>`，然后停下。
4. 不一致且该版本未安装时，给出 `seeed-zephyr install <版本>`，然后停下。
5. 没有 `snapshot.json` 的目录（仓库里的示例本身、手写项目）按当前版本构建。
6. `--allow-mismatch` 跳过判定，留给排查时故意用错配组合。
7. 环境变量 `ZEPHYR_WORKSPACE` 仍然优先，保留给构建矩阵使用。

版本不一致时停下，是因为 RP2350 的例子证明了错配会构建成功但真机失效。切换只要约 10 秒，停下让用户确认的代价很小。

`info` 增加两行: 工作区路径，以及工作区当前展开的版本。这两行读自磁盘（Zephyr 的 `VERSION` 文件），不来自代码常量。

## 9. 与现有机制的关系

- `use <版本>` 按顺序做三件事: 把仓库签出切到该 tag；把 Zephyr 切到映射表里的版本；从缓存还原二进制文件。`update --version` 保留，内部走同一条路径。
- setup 脚本里现有的 `sync_manifest_revision` 正是“切换 Zephyr”这一步的雏形，扩展它而不是另起一套: 增加打本地引用、按缓存还原二进制文件两步。
- 用户现有的 `~/zephyrproject` 原地升级，不搬目录: setup 写入模块筛选和缓存配置，给当前版本打引用。筛选后不再使用的模块目录（约 4G）由 west 标为未启用，setup 列出这些目录，经用户确认后移入回收站。
- 包模式（pip、pipx、Homebrew）下，示例和 metadata 随包版本走，`use` 只切换 Zephyr 工作区和版本对记录。Homebrew 安装仍然不支持在包管理器里回退版本。
- VS Code 插件在 CLI 命令稳定后接入: 版本选择界面调用同一组命令，环境信息里显示当前版本对。

## 10. 分期

第 1 期，存储方式和版本判定（不新增命令）:

1. setup 写入模块筛选和二进制文件缓存配置，原地升级现有工作区。
2. `build --app` 按 `snapshot.json` 判定版本，不一致时停下并给出命令。
3. `info` 打印工作区当前版本。

第 2 期，用户选版本:

1. 给当前基线打第一个仓库 tag，建立映射表。
2. 实现 `versions`、`install`、`use`。
3. 更新入门文档，说明版本对、磁盘占用和切换方式。
4. 插件接入同一组命令。

## 11. 验证方式

- 单元测试覆盖: 版本一致时构建、已安装但不一致时提示 `use`、未安装时提示 `install`、无 snapshot 时按当前版本、`--allow-mismatch` 放行、环境变量优先。
- 切换脚本测试: 两个版本之间来回切换，每次切换后二进制文件全部校验通过，git 清理后两个版本的存档都在。
- 真实构建: 两个版本各配自己的仓库跑完构建矩阵，RP2350 串口落在 USB。
- 待补: 烧录工具在共用 Python 环境下跨版本是否可用，目前只验证了构建。

## 12. 不在本次范围内

- 不改变示例内容和板级支持范围。nRF54LM20A、nRF54LM20B、STM32C5 仍按原计划单独推进。
- 不引入新的第三方依赖。版本切换只用 git 与 west 自带功能。
- 不自动删除已安装版本或缓存。释放磁盘由用户显式执行。
